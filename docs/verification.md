# Проверка и демонстрация

## Среда и данные

Проверено 11 ноября 2026 года по времени Asia/Qyzylorda:
Windows, Python 3.12, MongoDB **8.3.11**, FastAPI и PyMongo. Точные версии Python-пакетов
закреплены в `../requirements.lock`. Использована локальная MongoDB на порту 27017.

Генератор создал 100 пользователей, 60 моделей и 100 000 взаимодействий. Все характеристики
моделей синтетические. CLI-демонстрация затем добавила один просмотр; это ожидаемое изменение
счётчика и не является повторной загрузкой генератора.

## Автоматические проверки

Команда `python -m pytest -q`: **18 passed**.
В среде есть одно предупреждение зависимости Starlette о будущем переходе тестового
клиента с httpx на httpx2; текущие проверки завершились успешно.

Проверенные сценарии:

- JWT: подпись, срок действия и разрешённый алгоритм.
- Пользователь не может назначить себе роль администратора или передать чужой user_id.
- Уникальность email после нормализации, модели и её версии.
- Административные операции недоступны обычному пользователю.
- Пароль хранится как Argon2id-хеш и не попадает в ответы API.
- Прямая запись некорректного документа отвергается MongoDB с кодом 121.
- Восемь конкурентных повторов одного события дают одну запись и семь ответов-повторов.
- Идемпотентный повтор с другим payload возвращает 409.
- Архивирование модели сохраняет историю и запрещает новые взаимодействия с ней.
- Пагинация не пропускает записи при равных timestamp и не раскрывает чужую историю.
- Поиск и фильтрация совместимы с текстовым индексом на настоящей MongoDB.
- Подбор учитывает профиль, сигнал и ограничения ресурсов.
- При повторной оценке в среднем участвует только последняя оценка каждого пользователя.
- Агрегации статистики модели, популярности и активности возвращают ожидаемые результаты.
- Повторный seed с теми же параметрами не увеличивает объём данных.
- Индексный и полный просмотр возвращают одинаковые результаты на тестовом наборе.

Проверка Ruff включена в инструкцию запуска. Проверка реального HTTP-сервера и CLI выполнена
через `python -m app.cli demo`; Swagger UI также открыт и визуально проверен в браузере.

## Эксперимент с индексом

Исходный результат: `../output/benchmark.json`. В момент измерения было ровно 100 000 событий.
Запрос получает последние 20 событий одного пользователя по `created_at DESC, _id DESC`.
Каждый путь выполнен пять раз; для всех запусков набор результатов совпал.

| Показатель | Принудительный полный просмотр | Индекс user_recent |
|---|---:|---:|
| Возвращено записей | 20 | 20 |
| Просмотрено документов, медиана | 100 000 | 20 |
| Просмотрено ключей за запуск | 0 | 20 |
| Основные стадии | COLLSCAN, SORT | IXSCAN, FETCH, LIMIT |
| Время по explain, медиана | 62 ms | 0 ms |

Состав индекса: `{user_id:1, created_at:-1, _id:-1}`. Количество просмотренных документов
уменьшилось в 5 000 раз **для этого запроса на этом наборе**, что не означает такого же
ускорения всей системы. Размер индекса в момент измерения — 2 654 208 байт.

`0 ms` — значение счётчика MongoDB с миллисекундным разрешением, а не физически нулевое
время. Использован принудительный `hint` для изоляции путей доступа; кэш не очищался.
Не измерялись конкуренция, нагрузка, p95/p99 и скорость записи. Индексы требуют места и
обновляются при записи; поэтому добавлены под перечисленные запросы, а не под каждое поле.

## Сценарий защиты на 5–7 минут

1. Объяснить: пользователи — исследователи; items — версии моделей; interactions — действия.
2. Показать три коллекции в MongoDB Compass и один документ каждой, скрыв password_hash.
3. Обосновать вложенные параметры и отдельную неограниченную историю.
4. Открыть `/docs`, показать регистрацию, вход и защищённую запись каталога.
5. Выполнить поиск по сигналу/категории и показать курсор следующей страницы.
6. Запустить CLI demo, показать историю и ограниченный подбор под устройство.
7. Показать агрегированные оценки и объяснить, почему повторная оценка не увеличивает вес.
8. Открыть `output/benchmark.json`: одинаковые результаты, 100 000 против 20 документов.
9. Показать `$jsonSchema`, уникальный индекс и результат тестов.

Для скриншотов финального отчёта нужны реальные окна Swagger, MongoDB Compass со схемой
и индексами, результат pytest и планы explain. Текст отчёта подготовлен отдельно;
скриншоты не подменяются нарисованными результатами.

## Проверка Docker

Compose-конфигурация проходит `docker compose config --quiet`. Команда
`docker compose build api` успешно собрала образ `bd6-api` с закреплёнными зависимостями.
Одноразовый контейнер с `--network none` успешно импортировал приложение, построил
OpenAPI-схему с 13 путями и создал каталог результатов от пользователя UID 10001.

В последующей проверке полный Compose-стек также запущен и проверен: MongoDB 8.0.34,
18 успешных тестов внутри Docker, CLI, HTTP-запросы и сохранность после перезапуска.
См. `docker-verification.md`. Для Docker теперь используются порты 8001 и 27018,
поэтому локальная MongoDB на 27017 не затрагивается. Локальные измерения выше и
контейнерные измерения в отдельном документе относятся к разным запускам.
